STEP 1 — WHAT ARE WE ACTUALLY MINIMIZING

Same grid, every step of the way

The setup

Start at the top-left cell, (0,0). Reach the bottom-right cell, (2,2). You can move up, down, left or right.

Every move between two cells costs an effort:

effort = abs(height[next] - height[current])

A path is a sequence of moves. Its cost is not the sum of the moves — it's the single worst move on that path.

path effort = max(all edge efforts on the path)

We want the path whose worst move is as small as possible.

Poora path itna hi "bura" hai jitna uska sabse bura kadam. Baaki sab kadam irrelevant hain.
Pick a path below to see how its effort is computed.
WHY NOT SUM?

Sum tells you the wrong story

If we summed the edges, a path with many small, gentle moves could lose to a path with one brutal cliff. But a hiker doesn't care about total distance walked — they care about the steepest single step they're forced to climb. That's exactly what "effort" models here: the bottleneck, not the total.

Try both paths on the right. Notice: the path with the lower sum is not always the path with the lower max. That's the whole problem, in one grid.

STEP 2 — IF I KNOW NOTHING ABOUT OPTIMIZATION

"What can I do?" — try every path.

If I know nothing about optimization, what can I do? Explore every path from start to destination, compute each one's effort (its worst edge), and keep the smallest. That's it. No cleverness yet.

At every cell: look at unvisited neighbours, step into one, and ask the exact same question again — "what's the best I can do from here?" That repetition is recursion. We carry one running value downward as we go: maxi, the worst edge seen so far on this path.

Har cell par bas itna sochna hai: "yahan tak ka sabse bura kadam kitna bada tha?" — aur wahi maxi neeche carry hota hai.

STEP 3 — SOMETHING'S WASTEFUL

Two different paths, same future

Notice something: multiple different paths can arrive at the same cell X. Once you're standing at X, everything ahead of you — every neighbour, every future decision — is identical, no matter which road brought you here.

Future same hai — ise dobara solve kyun kar raha hoon?

The brute force above re-explores that entire future every single time it reaches X. That's the waste. We need to remember: "the cheapest way I've reached X so far is ___" — and never redo work that can't beat it.

INTRODUCING bestEffort[cell]

One number per cell: the best effort so far

The rule

visited means "currently in my path" — it prevents walking in circles during one attempt.

bestEffort[cell] means "the best (smallest) effort with which I have ever reached this cell." If a new arrival can't beat that record, there is nothing new to discover — skip it.

STEP 4 — WHICH CANDIDATE NEXT?

Three cells are waiting. Which do we process first?

Say three frontier cells are candidates to expand next, each reached with some effort:

Which should I process first? The one with the smallest effort, . Here's why: once you commit to expanding a cell, you're claiming "this is the best possible arrival here." That claim is only safe if nothing cheaper could still show up later — which is guaranteed only for the smallest candidate on the frontier, since every other unexpanded route can only get more expensive from here (effort only ever grows or stays the same as we extend a path).

Smallest effort waala hamesha safe hota hai process karne ke liye — usse sasta kuch aane wala nahi.
STEP 5 — FINDING THE SMALLEST, EFFICIENTLY

Scanning the frontier every time is slow

Smallest candidate efficiently kaise milega? Re-scanning every frontier cell each time is O(n) per pick. We want a structure that always hands us the minimum instantly, and re-sorts itself cheaply when new candidates arrive.

That structure is a min-heap / priority queue. Push a candidate in — O(log n). Pop the smallest — O(log n). Watch it below: candidates enter, the heap always keeps the smallest on top, and popping the top gives you exactly the order Step 4 said was safe.

Heap is empty. Insert a candidate to begin.

This is Dijkstra's algorithm. Not memorized — assembled: always expand the smallest known effort next (Step 4), and get that minimum efficiently with a min-heap (Step 5). Track one number per cell (Step 3) so we never redo settled work.

REBUILD MODE

Conceptual hints, not code

  • What do you need to try? Every neighbour, from every cell, without revisiting a cell mid-path.
  • What travels with you? The worst edge seen so far — one running number.
  • What do you record per cell? The best (smallest) effort that has ever reached it.
  • What decides your order? Always expand the frontier cell with the smallest recorded effort.
  • What structure gives you that instantly? A min-heap keyed on effort.
  • When do you stop? The moment the destination is popped — that pop is provably optimal.
